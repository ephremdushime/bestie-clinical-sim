# Product specification — Bestie Clinical Sim 1.0.0

## Product intent

An interactive clinical education and assessment platform that helps learners practise clinical reasoning and lets educators evaluate student performance using controlled fictional cases. The platform is an educational tool, not an autonomous diagnostic or treatment system.

## Two operating modes

### Learning and practice
- Students choose from the case library.
- Patient interaction is conversational and uses fixed case facts.
- Hints are available; the learner can repeat a case by starting a new session.
- Students request tests only after documenting a clinical indication.
- The case engine returns preconfigured results or explicitly says that no validated result is configured.
- Students submit differentials, final diagnosis, management and a short interpretation/reflection.
- The report gives formative feedback and limitations.

### Teacher-led examination
- Educator creates an exam with title, hidden case, duration and pass-mark threshold, and shares a unique exam code.
- The learner joins by code; the backend chooses the exam's case regardless of the learner's submitted case ID.
- The public case list contains no hidden diagnosis or fixed case facts.
- No hints are offered in exam mode. Initial vitals are not displayed in the patient panel; learners may ask for information through the encounter.
- The API refuses new chat/investigation actions after the exam duration elapses. Learners can submit their current work after time expires.
- The educator dashboard lists sessions, reports and event logs. This is a prototype gate and not a secure exam platform: shared codes/tokens can be passed to others, and identity is not verified.

## Clinical encounter flow

1. Introduce self, establish rapport, explain and obtain consent.
2. Take a focused history and identify red flags.
3. Request relevant examination findings and observations.
4. Form a differential diagnosis.
5. Select investigations and record why each is indicated.
6. Review case-configured laboratory/imaging results and interpret them.
7. Submit diagnosis, immediate management, medication safety, referral/escalation, follow-up and safety-netting.
8. Review the feedback report with an educator.

## Case library

Six starter fictional cases: malaria, severe respiratory presentation, burn with possible inhalation injury, road traffic trauma, pregnancy with severe headache, and pediatric fever/fast breathing. They are illustrative drafts, not clinically approved case files. Educators must verify all thresholds, investigation results, treatment pathways and referral decisions against current local protocols.

## Investigation engine

The API stores fixed results per case. The student supplies a free-text indication; the system logs the indication and returns a configured result. If a test is not configured for the case, the API does not synthesize a result. The prototype gives a basic indication feedback flag; it does not yet assess indication quality semantically or enforce a complete order set. Some imaging cases show vector schematics only, explicitly labeled as synthetic illustrations.

## AI responsibilities and boundaries

- Patient role-play: bounded dialogue consistent with fixed facts, plain English and no diagnosis reveal.
- Case drafting: creates a structured draft only; source notes are untrusted input, references are not independently verified, and educator approval is mandatory.
- Feedback: can support future explanatory feedback, but the current numeric score comes from transparent demonstration checks rather than a validated LLM evaluator.
- Clinical truth: controlled by case data and educator-approved rules, not freely generated by a language model.

## Proposed assessment domains

Communication/history, severity/examination, investigation choice and indication, result interpretation, differential diagnosis, final diagnosis, management/safety, referral/follow-up. The prototype flags some missing escalation actions in high-risk cases. This rubric is incomplete and not psychometrically validated. A high total must never compensate for a critical safety error in a validated future version.

## Immersive roadmap

The current WebXR capability check and headset-style interface are scaffolding only. Future work with Uniport should validate browser/headset compatibility, controller input, patient avatar representation, accessibility, motion comfort, performance, and offline/network behavior. Clinical content should remain presentation-independent so browser, VR and AR clients share the same case facts and scoring engine.

## Acceptance criteria for a supervised pilot

- Educator reviews and signs off each case and rubric version.
- No diagnosis/facts leak through public case listing or learner-side code.
- All test orders record indication and produce only configured results.
- Exam code assigns the educator-selected case; exam duration is enforced server-side for new actions.
- Reports and event logs are retrievable by an authorized educator.
- No real patient-identifiable data is collected.
- Student-facing limitation statement and appropriate institutional approvals are in place.
